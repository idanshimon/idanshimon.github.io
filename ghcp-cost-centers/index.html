How GitHub Copilot cost centers actually work

On June 1, 2026, GitHub Copilot stopped charging flat per-seat requests and started metering AI credits. Suddenly a heavy team could drain a pool that everyone's licenses paid into. Cost centers are the fix — but the docs are half-shipped, the official automation sample still targets a retired billing unit, and "give a group more credits" means something more specific than it sounds. This is the verified version.

by Idan Shimon · July 2026 · verified against the GitHub REST API and changelog, not the marketing

The pricing change was abrupt, and for a few weeks the tooling half-worked. An admin I was helping described the pattern exactly: an API call he needed to automate budgets "just didn't work," so he logged in every couple of days and retried, and one day it "magically started working." That's the texture of this whole area right now — features shipping fast, docs trailing the API, endpoints appearing and disappearing between billing cycles. So everything below is checked against what the API actually returns today, and I've flagged the places where the official documentation and sample code are still behind.

The model in one paragraph

Copilot usage is metered in AI credits — one credit is one US cent. Each Business seat includes $19/month of credits, each Enterprise seat $39/month, and by default every seat's credits are pooled at the enterprise level. One shared pool. That pooling is the point (light users subsidize heavy ones) and also the problem: nothing stops one team burning through credits that another team's licenses funded. A cost center carves a group out of that shared model — its own fenced pool, its own budget, and optionally its own Azure subscription to bill overage against.

The distinction everyone gets wrong: a cap is not a reservation

This is the single most important thing to internalize before you configure anything, because the mental model failure here is what makes people think the feature is broken.

When you put ten users in a cost center, the pool it gets is the sum of those ten seats' included credits — nothing more. The included-usage cap on the cost center fences that group: it stops them drawing more than their own licenses fund, which protects everyone else. What it does not do is mint extra credits. If those ten users want to spend more than their ten seats include, the cap can't conjure it.

So there are exactly two ways to give a group more capacity, and neither is a magic number in a settings box:

1. Assign more (or higher-tier) licenses to the cost center — the pool is computed from licenses, so more seats means a bigger fenced pool.

2. Attach the group's own Azure subscription and let them run metered overage against a cost-center budget. That spend bills to them, at $0.01 per credit, and never touches the enterprise pool.

Once you see it this way, the confusing questions answer themselves. "Can I give this team $10K/month without taking from everyone else?" Yes — their Azure subscription funds the overage, the fence keeps it isolated. "Can I just raise their per-seat credit number?" No — that number is fixed by the license tier; you scale with licenses or with paid overage. The cost center is a fence, not a faucet.

The four controls, and which ones actually stop spend

ControlWhat it limitsHard stop?
User-level budget (universal / cost-center / individual)One user's total credit use — pooled and meteredAlways
Included-usage cap (the AI credit pool on a cost center)How much of the shared pool a cost center can drawBlock or allow overage
Cost-center budgetA cost center's metered spend after its poolOnly if "stop usage" is on
Enterprise / org budgetMetered spend at that scopeOnly if "stop usage" is on

Two things bite people here. First, precedence: individual budgets beat cost-center budgets beat the universal default, and across scopes the most restrictive one wins. A low enterprise-wide budget can block a cost center before its own, higher budget is ever reached — so if someone gets blocked unexpectedly, check every scope that applies to them, not just the obvious one. Second, and this is the quiet one: "stop usage when the budget is reached" is off by default on cost-center, org, and enterprise budgets. Without it, the budget alerts you but keeps letting spend through. User-level budgets are the exception — they always hard-stop.

The setup, verified

You can do the first one in the UI to get oriented — Billing and licensing → Cost centers → New cost center, optionally attach the group's Azure subscription, add an enterprise team as the resource (membership then syncs from your IdP automatically), then create a SKU-level budget scoped to it. But the whole thing is REST-driven, and the API is where this belongs once you're past the first one. You need an enterprise owner or billing-manager token with manage_billing:enterprise (and read:org for team sync). Replace ENTERPRISE with your slug.

Create the cost center

gh api --method POST \
  -H "X-GitHub-Api-Version: 2022-11-28" \
  /enterprises/ENTERPRISE/settings/billing/cost-centers \
  -f 'name=Team-Name'
# → { "id": "<COST_CENTER_ID>", ... }  — keep the id

Add the team (membership auto-syncs)

gh api --method POST \
  -H "X-GitHub-Api-Version: 2022-11-28" \
  /enterprises/ENTERPRISE/settings/billing/cost-centers/ID/resource \
  --input - <<< '{ "enterprise_teams": ["team-slug"] }'

Prefer enterprise_teams over listing individual users — team membership flows into the cost center and stays current as people join and leave, so you're not maintaining a roster by hand. One constraint worth knowing: once the AI credit pool is enabled, only users and enterprise teams are valid resources — not organizations or repositories, because those carry no per-license entitlement to compute a pool size from.

Set the AI-credits budget

gh api --method POST \
  -H "X-GitHub-Api-Version: 2022-11-28" \
  /enterprises/ENTERPRISE/settings/billing/budgets \
  -f budget_type='SkuPricing' \
  -f budget_product_sku='copilot_ai_credits' \
  -f budget_scope='cost_center' \
  -f budget_entity_name='ID' \
  -F budget_amount=1000.0 \
  -F prevent_further_usage=true

The SKU string is copilot_ai_credits.

One place the official material is still behind

This is the part you won't get from the docs, and it's the reason to verify rather than trust. The included-usage caps are API-only right now. The changelog is candid about it: the cost-center settings UI for the AI credit pool is "coming soon," and today the capability lives entirely in the REST API. If your workflow is UI-driven you're waiting; if you automate, this is a non-issue — arguably a feature, since it's scriptable from day one.

What to build if you're automating this

The most useful thing I can pass on isn't a command, it's an architecture note, because the interesting constraint only shows up once you try to run this continuously.

The per-user usage report gives you a point-in-time snapshot — every user's consumption at the moment you call it — not a historical time series. An earlier endpoint returned usage-per-user-per-day up to the current date; it broke during the June transition and, at least for a while, didn't come back. That history is what actually matters, because the signal you want isn't "who is over budget right now," it's rate: last month twenty people hit their limit in the final ten days; this month sixty hit it before the fifteenth. That trend is what tells you to buy more Enterprise seats — before your developers hit walls, not after.

So don't depend on GitHub retaining the history. Treat their report as a sensor you sample, and build the time series yourself:

Snapshot on a schedule (daily is plenty, twice a day near month-end) and append each pull to your own store, keyed by (user, date). Compute the per-day delta at ingest, not just the running total — burn rate is the number that drives everything. Make the pipeline idempotent and gap-tolerant, because the API will flake and a missed day shouldn't corrupt your deltas. And split the three jobs so they fail independently: a collector that writes raw snapshots, an analyzer that reads the store, and an actuator that makes the budget writes. Then a broken report pull can't scramble your budgets, and you can re-run the analyzer over history without touching the API.

Do that and the missing-history problem disappears — you own the series, you can project each user's exhaustion date from their recent rate, and the same pipeline that rebalances budgets also produces the "we need N more seats by date" number on its own. The billing report becomes a sensor; your store becomes the source of truth.

The short version

  • Copilot is metered now; one credit is one cent; seats pool at the enterprise level by default.
  • A cost center fences a group to its own licenses' worth of the pool. It protects the others; it does not add credits.
  • "More for this group" = more licenses, or their own Azure subscription running metered overage. Nothing else.
  • Included-usage caps are REST-only today; "stop usage" is off by default on cost-center budgets; the most restrictive budget across scopes wins.
  • If you automate, own your own usage time series. GitHub's report is a snapshot; the rate of change is the number that matters.

Everything here is drawn from the GitHub Enterprise Cloud documentation, the GitHub changelog, and the REST API as they stood in July 2026. This area is moving fast enough that some of it will be stale by the time you read it — which is rather the point. Check the API.

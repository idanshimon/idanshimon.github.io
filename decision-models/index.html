Not every agent step needs a generated answer.

What testing Kev taught me about decision models, evaluation, and where generative AI still belongs.

by Idan Shimon · September 2026

Many steps inside an AI agent end with a choice, not a paragraph. Which category fits this passage? Whose statement is it? Does the evidence support taking the next step?

That is what interested me in TypeSafe's Jev and Jared Palmer's open-source Kev. These are not projects I built. I wanted to understand the decision-model approach and test one implementation against a small, concrete task.

The idea is straightforward: when the application needs a bounded decision, score the available answers directly instead of generating text that the application then has to interpret.

But a faster choice is only useful if it preserves what the evidence actually says.

01What a decision model changes

A general-purpose language model can classify text perfectly well. Ask for structured JSON, validate the result, and use the selected label. That is a reasonable baseline, not an architecture to dismiss.

A decision model changes how the answer is produced. In the Kev implementation I inspected, a Qwen-based model scores supplied options rather than generating an answer token by token. Its interface supports multiple-choice, yes/no, and rating questions.

Classification is not new. The interesting part is making task instructions and answer choices part of a reusable model interface, rather than building a separate fixed-label classifier for every task.

Two names need separating:

  • Jev is TypeSafe's hosted model and API.
  • Kev is Jared Palmer's independently developed, open-source reconstruction of a Jev-style approach, which you can run and train yourself.

My measurements below are of Kev-4B, not hosted Jev. Similar interfaces do not establish identical internals or performance.

02A small test with a practical question

I used 60 synthetic finance-commentary passages to test a distinction that matters in extraction: “I bought,” “someone else bought,” and “I might buy” do not mean the same thing.

The passages covered six categories: an explicit position, a conditional setup, news, someone else's view, promotion, and unclear content. Each system classified the same passages; expected labels were withheld from model inputs.

Kev ran on a Tesla T4 in FP16 with an unmerged adapter. GPT ran through Azure OpenAI. GLiClass's configuration performed poorly on this task; that alone does not identify whether label wording, checkpoint choice, or runtime setup was responsible.

This was a diagnostic, not a production leaderboard. The categories overlapped, instructions differed between systems, and the rules were developed alongside the examples. The counts describe these runs, not a general ranking of the models.

03The disagreement that made the problem clearer

One passage was more useful than the headline score:

Should the jobs number come in soft, I'd add to my rate-cut trades. It hasn't yet, so no move.

Our expected label was conditional. Kev selected explicit position.

There is an important nuance: “my rate-cut trades” does suggest an existing position. What has not happened is the proposed addition. A single content-type label compresses both facts into one answer.

If a downstream system treats “explicit position” as evidence of a newly executed trade, it can misrepresent the passage. The failure to guard against is that interpretation, not merely disagreement with a label.

This points to a better experiment: separate the questions.

  • Whose position is being discussed?
  • Is the proposed action completed, conditional, or unclear?
  • Does the passage establish that a new action occurred?

Those are proposed improvements, not results from a follow-up run. They also make the evaluation more useful: test whether the system preserves attribution and action status, rather than only whether it matches one broad category.

04Confidence is useful only if the system can defer

Kev returns scores over the choices. That creates an opportunity to pass ambiguous cases to another model or a reviewer.

In a follow-up analysis of the saved scores, requiring a gap of at least 0.5 between the two highest probabilities accepted 41 passages and deferred 19. All 41 accepted predictions matched our labels.

That is an interesting development clue, not a validated reliability guarantee. The threshold was examined after seeing the results. It needs to be fixed on separate calibration data and evaluated on untouched examples.

The useful measurement is not confidence alone. It is how many cases the system accepts, how many accepted answers are wrong, and what happens to the cases it defers.

05Why the first prediction took 84 seconds

The timing initially looked strange: Kev's first prediction took 84.2 seconds. The remaining 59 had a median of 147 milliseconds.

Checking the source changed the interpretation. At the exact Kev revision used in the test, its serving code explicitly warms the model before accepting requests. The comment says this compiles the DeltaNet kernels and takes approximately one minute when uncached. It also persists the compiled-kernel cache between starts.

Our diagnostic runner did not perform that warmup before timing the first prediction. The observed delay is consistent with documented first-use kernel compilation and autotuning. We did not profile how much of each second belonged to those operations.

So neither “Kev takes 84 seconds to decide” nor “Kev always answers in 147 milliseconds” is a fair summary.

Model loading, first execution, and subsequent predictions are separate measurements. A service can warm up before becoming ready, but startup and idle infrastructure still belong in its operating costs. This run also lacked an optimized causal-convolution kernel, so it was not a performance ceiling for Kev.

06Where I would use this approach

The architecture I would test combines three kinds of work:

  1. Rules for exact checks, permissions, and requirements that can be expressed deterministically.
  2. Decision models for bounded semantic judgments over evidence, with a tested deferral path.
  3. Generative models for explanations, open-ended investigation, and tasks that genuinely require composing an answer.

A decision model does not become an authorization system because it returns a probability. Nor does choosing from a list replace investigation of a problem nobody anticipated.

The economic test is equally concrete: does the classification step avoid more expensive work, reduce rework, or improve an outcome? If the full extraction model still runs unchanged on every passage, adding a classifier adds inference work rather than automatically saving it.

I would not replace the existing extractor based on this diagnostic. I would test hosted Jev directly, align the comparison instructions, and evaluate separate decision dimensions on independently reviewed passages.

The opportunity is not to replace every generative model. It is to stop treating every step as a generation problem, then measure whether a more specific tool actually helps.

Which step in your agent workflow only needs a decision, and how would you know when that decision is wrong?
